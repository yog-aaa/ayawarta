# Cloudinary media management

## Current state

The completed invitation-media migration placed 31 physical assets in Cloudinary cloud `uhwi7xvb`: 27 images and four audio files, including one explicit hero and one audio asset for each of `rika-fauzi`, `shidqi-mita`, `dudi-aini`, and `default-preview`. The repository no longer contains the 12 legacy dynamic images or the hard-coded invitation modules. A separate Classic Rose upload added 35 optimized static theme and sample-photo assets to the same Cloudinary cloud. Payment and other static UI artwork remains in `public/images/`.

Classic Rose now serves small WebP texture, preview, portrait frame, and ornament derivatives from Cloudinary. Versioned delivery URLs are recorded in `src/config/classic-rose-cloudinary.json`; the local PNG sources and optimized WebPs are under `assets/themes/classic-rose/`, outside `public`. `scripts/optimize-classic-rose-assets.mjs` rebuilds derivatives; a background that previously ranged from about 5–25 MB per variant is now a seamless texture of about 7–83 KB. The tile generator flattens transparent source backgrounds against each variant's canvas color before mirroring, so no dark center line appears. The former identical red `event-frame.png` corner in every color variant is no longer rendered; event corners are drawn in CSS from the variant's primary color. The five fictional default-preview photos were generated specifically for the template and prepared with `scripts/prepare-classic-rose-preview.mjs`.

Run `node scripts/optimize-classic-rose-assets.mjs` after changing a variant's source PNG artwork. To replace the fictional demo photography, run `node scripts/prepare-classic-rose-preview.mjs <couple> <walking> <details> <groom> <bride>` with five source image paths in that order. `node scripts/upload-classic-rose-assets.mjs --dry-run` inspects the 35 local WebPs without network writes; `--execute` uploads missing content-addressed assets with overwrite disabled, verifies Cloudinary metadata and writes the URL manifest; `--verify` checks the remote assets and committed manifest without uploads. Commit the local source changes and manifest together. `src/lib/theme-config/classic-rose-assets.test.ts` enforces file size, texture dimensions and delivery URL shape.

Only the `default-preview` presentation swaps its stored photo URLs for the new Cloudinary sample assets through `src/features/invitations/default-preview-assets.ts`. The persisted record, canonical catalog, and all real customer invitations remain unchanged. The sample gallery omits the stored external video at presentation time to keep the demo coherent and avoid a duplicate poster image. Responsive theme and sample images use Cloudinary's direct image loader, which requests width-specific `f_auto/q_auto` derivatives; the seamless background texture and CSS mask use their already-small original WebPs.

The T3 Siger Priangan route currently uses CSS paper, relief, and gallery/portrait placeholders for its illustrative sample. No Siger concept PNG is a runtime asset or Cloudinary manifest entry. Private draft preview also shows explicit missing-photo placeholders; those images remain required before publication. Existing-invitation editor choices are loaded from deliverable Cloudinary assets already associated with that invitation, with matching image/audio types. An asset shared with another invitation can remain in its existing published slot but cannot be selected for a new slot. A5 now provides verified, draft-owned image choices for saved new drafts, behind a default-disabled feature gate and pending Neon migration. T4 owns culturally reviewed Siger artwork, optimized runtime derivatives, and verified media delivery; the current static route does not imply an upload or production customer conversion.

The Git-tracked [canonical catalog](../src/features/media/canonical-catalog.ts) is the portable seed input. Each record binds a slug, category, folder, public ID, format, resource type, metadata, and HTTPS delivery URL. The optional gallery video URL is invitation content in PostgreSQL, not a Cloudinary asset. Cloudinary audio uses provider resource type `video` and domain resource type `AUDIO`.

## Naming and validation

The canonical migration IDs follow `ayawarta/production/invitations/{slug}/{category}/{item}`, with `couple`, `gallery`, and `audio` categories. A5 new-draft images instead use `ayawarta/production/invitations/draft-{draftId}/images/{provisionId}-{digest-prefix}` so an unpublished slug change cannot change ownership. A target URL must bind to its exact public ID, expected cloud, upload resource type, version, and extension. Seed validation rejects a missing hero, partner photo, gallery image, audio resource, or inconsistent category.

## Operational checks

- `pnpm test src/features/media/canonical-catalog.test.ts` validates the portable catalog without external files or network access.
- `pnpm media:verify-upload` checks the local Stage 5B upload report's schema, counts, public ID uniqueness, required hero/audio IDs, URL shape, and summary consistency **offline**. It requires the ignored `.media-migration/cloudinary-upload-report.json` artifact. This command does not check its pinned SHA-256, compare every asset with the canonical catalog, or contact Cloudinary to confirm current live state.
- `pnpm media:verify-audio` validates the three operator MP3 inputs when `.media-migration/input/audio/` is available.
- `pnpm exec vitest run --config vitest.integration.config.mts src/features/media/canonical-provenance.integration.test.ts` is the fail-closed provenance check. It verifies the report's pinned SHA-256 and 1:1 metadata against the canonical catalog and guarded local PostgreSQL. It requires the accepted report and seeded local database; it also runs as part of the full `pnpm test:db` suite (which requires running the preflight database target check first, as other integration tests connect directly to `DATABASE_URL` without internal guards). The historical Stage 5B streaming identity audit supplied live content evidence at migration time; none of these offline commands establish current live Cloudinary content identity.

The historical `media:dry-run`, `media:migrate`, `media:verify`, and `media:audit-identity` package scripts were retired after migration. Their source files remain as historical tooling. They require removed legacy sources and must not be used as routine upload commands.

## A5 draft uploads and safe reruns

Stage A5 adds an administrator image workflow for **saved new private drafts** (cover, portraits, and gallery). It is disabled by default and its additive database migration has not been applied to Neon. The server checks file signature, declared type, decoded dimensions and pixels, and input byte limits; it creates a slot-sized WebP derivative with Sharp. It reserves a `DraftMediaProvision` row before upload, uses a deterministic public ID rooted in the immutable draft ID, uploads with overwrite disabled, reads the remote metadata and content back, and only then creates a linked `MediaAsset` record. A failed link leaves a recoverable reservation for readback or same-file retry; it never changes the public invitation or deletes a Cloudinary asset. The verified image must still be selected and saved in the draft before publication. New audio upload remains outside A5, while music itself is optional.

The draft and its admin controls are private, but a Cloudinary delivery URL is an unlisted public URL as soon as the upload succeeds. The uploaded image does not appear on the guest invitation until an explicit publication. Do not describe Cloudinary storage itself as private or use draft media for content requiring access-controlled storage.

The older `prepareImage` primitive remains the first normalization step. A5 configures its 15 MiB input ceiling explicitly, then produces a WebP derivative capped at 3 MiB; decoded pixels are still limited. The four historical invitations keep their canonical catalog and same-invitation media rules. A5 verified uploads are scoped by `DraftMediaProvision.draftId` while the draft is unpublished, so another customer's or another draft's image cannot be selected simply by knowing its media ID. After first publication, the editor returns to the existing published invitation's media rules; unused draft uploads remain in the ledger but are not offered as choices. No production Cloudinary upload, Neon migration, or new customer publication has been performed by preparing this source.

Never overwrite a conflicting public ID merely to make a retry pass. A safe rerun first checks existing metadata and content identity; verified existing assets can be reused. A mismatch must stop for review. Keep Cloudinary API credentials on the server, do not expose them in logs, and do not delete resources from the old account. The [historical migration runbook](media-migration.md) records the completed one-time process and cleanup gates.
